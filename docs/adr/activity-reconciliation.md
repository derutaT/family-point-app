# ADR: 活動突き合わせ機能

> Keyword: `activity-reconciliation`｜関連: 仕様 `docs/spec/` / 計画 `docs/task_plan/` / タスク `TASKS.md`

各レコードは Context / Decision / Consequences / Alternatives で記す。
本機能の決定は相互参照が多いため 1 ファイルにまとめる（ADR が大きく増えたら 1 ADR = 1 ファイルへ分割してよい）。

## ADR-0001 検知まではせずに「表示により自分で確認する」方式を採る
- **Context**: 「申請できてない事が多いよね直そうね」といった気づきと促しをベースとした働きかけを子供にしたい。
- **Decision**: アプリは外部の実測値と並べて *人が気づける* 表示を提供するに留める。自動検知はしない。
- **Consequences**: 気づきと是正は人（子供）に委ねられる。
- **Alternatives**: 申請不足を自動検知しアラート表示を行うと受け手となる子供に過度なストレスを与えうるため、自動検知でのアラート表示や通知はやらない。

## ADR-0002 2つの独立した記録に分離する
- **Context**: 申告と実測は出所が別となり特性も異なるため別として取り扱うが好ましい。
- **Decision**: ポイントの記録（= 申告）と計測された記録（= 実測 / 外部Activity）を別データとして保持し、表示で突き合わせる。
- **Consequences**: 無理な統合が行われない。比較は join `(childId, date)` で行う。
- **Alternatives**: 単一の利用記録に統合 → 出所の区別が消え、整合が崩れる。却下。

## ADR-0003 現在値を保持し、イベントは振り返り記録として分離する
- **Status**: Proposed（未実装。整備タスクは T_001）
- **現状（コード）**: `state` は**残高中心**（`member.points` / `dailyPoints` を直接更新）で、`history` 配列が redeem/auto/approve を**部分的に**記録するのみ。日替わり付与は未記録、残高が真実の源（overview §2）。
- **Context**: Day/Week 表示・突き合わせ・履歴・自己申告には「いつ何が起きたか」の記録が要る。一方で残高は都度すぐ参照したい。
- **Decision**: 現在値（残高）は子供ごとに保持する権威データとして直接更新し、イベント（獲得/消費/日替わり付与）は**振り返り専用の追記記録**として分離する。**残高はイベントから導出しない（event sourcing は採らない）**。既存 `history` の流用か新規設計かは T_001 で判断する。
- **Consequences**: 残高の都度再計算が不要でシンプル・軽い（現コードの自然な延長）。取引ごとに残高更新とイベント追記の両方を行うため、1か所の関数に集約してズレを防ぐ。イベント記録で Day/Week・履歴・突き合わせが可能。localStorage 肥大化対策に古いイベントの日次ロールアップが要る（見直し条件は ADR-0004）。
- **Alternatives**: event sourcing（残高をイベントから導出）→ 都度の再計算・移行が重く本アプリには過剰。却下。残高のみ（イベント記録なし）→ 振り返り・突き合わせができない。却下。

## ADR-0004 インポート境界でバックエンドレスを維持する
- **Context**: スクショの AI 解析には vision モデル呼び出しが要り、単一HTML に置くと API キー / バックエンド問題が生じる。
- **Decision**: AI解析は *アプリ外の差し替え可能なツール* に置く。アプリは確定スキーマ（overview §4）の Activity を **インポートするだけ**。スキーマが両者の契約。
- **Consequences**: 単一HTML / バックエンドなしを維持。解析手段（手動入力 → AI → 将来別物）を自由に差し替え可能。
- **Alternatives**: アプリ内で vision 呼び出し → 構成を壊す / 鍵露出。却下。
- **見直し条件（Revisit）**: 次のいずれかが起きたら本決定（バックエンドレス維持）を見直し、新 ADR で supersede する。①複数端末での状態共有が必要になった ②データ量が localStorage 上限(約5MB)を超え運用に支障が出た。段階的選択肢の順序: IndexedDB 化（5MB 制約のみ解消・バックエンド不要）→ 同期レイヤ追加（複数端末同期）→ 本格バックエンド。

## ADR-0005 突き合わせ粒度は「子供×日の合計」（v1）
- **Context**: スクショから読めるのは日次・アプリ別合計まで。セッション単位は取れない。利用者は「あからさまな差」に気づければ十分とする。
- **Decision**: v1 は子供 × 日 の `chargeable` 合計で比較。項目単位照合は v2。
- **Consequences**: 実装が単純で誤検知が少ない。「どのゲームを隠したか」までは v1 では出ない（遊びイベントへの項目名記録で拡張余地は残す）。
- **Alternatives**: 項目単位の精密照合 → 過剰。スコープ外。

## ADR-0006 正直さは「報酬」ではなく「認知」で扱う
- **Context**: 自己申告に明示的報酬を付けると over-justification が起き、正直が報酬目当ての取引に化け、報酬消失で正直も消える。一方、純粋な損失だけだと「バレない立ち回り」を学習させる。
- **Decision**: 報酬を付けず、"自分で申告した事実" を親子に見える形で残す。インセンティブは既存の段階返済（自己申告 = 1倍 / 禁止破りバレ = 2倍）による *エスカレーション回避 + 信用* で表現する。
- **Consequences**: 内発的動機を壊さずに正直を後押し。新たな報酬機構が不要。
- **Alternatives**: 申告ボーナス付与 → over-justification と「申告稼ぎ」の攻略を招く。却下。

## ADR-0007 手動インポート先行・AI自動化は PoC ゲート
- **Context**: 最大の不確実性は「スクショから AI が安定して読めるか」。
- **Decision**: まず手動インポートで突き合わせ〜自己申告ループを完成させ、AI解析（解析くん）は別 PoC で検証 → 成功時に本実装して取り込みを自動化する。
- **Consequences**: AI の成否に依存せず先に価値を出せる。AI は後から差し込める。
- **Alternatives**: 最初から AI 前提で実装 → 不確実性が全体をブロック。却下。

## ADR-0008 強制はシステム外、システムは可視化まで
- **Context**: 既定運用は2週間に1度の親子レビュー。申請忘れ等は正常範囲。
- **Decision**: システムは「見えるようにする」までを担い、不誠実の常態化への対応（雷）は人（親）に委ねる。
- **Consequences**: システムが過度な監視 / 罰の主体にならず、「親子で共有する透明な記録」という方針と整合する。
- **Alternatives**: 自動ペナルティ → 厳格制御化し目的（バランス）と乖離。却下。

## ADR-0009 初期は強調・検出を行わず、純粋な並置に留める
- **Context**: 申告 vs 実測の差を閾値で「未申告/超過」と強調・フラグ付けするのは弱い自動判定であり、「システムは判定しない、人が気づく」(ADR-0001) と緊張する。まず子供自身の気づきを優先したい。
- **Decision**: v1 は比較ビューで2系列を並置するに留め、未申告・超過の強調・フラグ・検出は実装しない。気づきと自己申告は子供に委ねる。
- **Consequences**: 実装がさらに軽くなり ADR-0001 と完全に整合。閾値チューニングが不要。「どれだけ隠したか」をシステムは指摘しない。
- **見直し条件（Revisit）**: 子供が差に気づけない／意図的な隠蔽が常態化する、が観察されたら検出機能の追加を検討する（新 ADR で supersede）。
- **Alternatives**: 閾値で強調 → 弱い判定が入り方針と緊張。却下（将来の検討対象）。
